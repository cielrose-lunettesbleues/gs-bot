# Session Dev — 2026-06-10 : Migration SaaS multi-tenant

## Objectif de départ

Transformer le projet depuis son état initial (bot standalone mono-utilisateur piloté par `.env`) vers une **application SaaS multi-tenant** où plusieurs streamers peuvent se connecter à la même instance via OAuth Twitch, sans jamais toucher un fichier de configuration.

---

## Architecture résultante

```
Streamer → /setup (opérateur) → OAuth Twitch → /dashboard → OBS Browser Source
```

Point d'entrée principal : `src/server.ts` (`npm run dev`)  
L'ancien mode standalone `src/app.ts` est exclu de la compilation (`tsconfig.json`).

**Stack** : Hono + SQLite (better-sqlite3) + tmi.js + SSE overlay

## Fichiers créés

### `src/server.ts`
Serveur principal Hono multi-tenant. Remplace complètement `app.ts` pour le mode SaaS.

Routes :
- `GET /setup` — wizard premier lancement (redirige vers `/` si déjà configuré)
- `POST /setup` — sauvegarde les credentials Twitch, met à jour `oauthConfig` en mémoire
- `GET /` — login page ou redirect vers `/dashboard` si authentifié
- `GET /dashboard` — dashboard par utilisateur (session requise)
- `GET /auth/twitch` — initie le flow OAuth Twitch (state CSRF cookie)
- `GET /auth/twitch/callback` — échange le code, crée session, démarre le bot IRC en arrière-plan
- `POST /auth/logout` — invalide la session
- `GET /overlay/:channel` — page HTML OBS Browser Source (sans auth)
- `GET /overlay/:channel/events` — SSE stream pour l'overlay OBS
- `GET /api/status` — état du tenant (config, queue, approbations, overlay, Twitch)
- `GET /api/history` — historique de lecture
- `PATCH /api/config` — modification de config à chaud
- `POST /api/queue/stop` — stop d'urgence
- `POST /api/cooldown/reset` — reset cooldown
- `POST /api/approve/:username` — approbation mod
- `POST /api/deny/:username` — refus mod
- `POST /api/simulate` — simulateur de chat depuis le dashboard

## Décisions d'architecture

### `oauthConfig` comme objet mutable
Le middleware `sessionMiddleware(db, oauthConfig)` capture `oauthConfig` par référence. Après le wizard `/setup`, `oauthConfig.clientId` etc. sont mutés en place → pas besoin de restart serveur.

### Bot IRC non-bloquant
`tenant.twitchBotManager.start()` est lancé en fire-and-forget après la création de session dans le callback OAuth. Le streamer atteint toujours le dashboard même si tmi.js est lent ou échoue à connecter.

### URL overlay : double rendu
Le span `#overlay-url` est pré-rempli côté serveur avec `/overlay/${channelName}`. Le JS le remplace avec l'URL complète (`window.location.origin + path`). Robuste même si JS échoue partiellement.

### Services isolés par userId
Chaque streamer a ses propres instances (`PlaybackQueue`, `TwitchBotManager`, etc.) dans `TenantManager`. Pas de partage d'état entre tenants.

## Mots interdits dans les textes (2026-10-14)

Le texte d'un `!gs ... |texte` partait à l'écran et dans la voix du TTS sans
filtre. Une liste de mots interdits par tenant a été ajoutée.

### Ce qui a été ajouté

- table `banned_words (user_id, word)` + `addBannedWord` / `removeBannedWord` /
  `listBannedWords` dans `src/db/database.ts`
- `src/moderation/bannedWordsService.ts` : `normaliseText` (minuscules, accents
  retirés, espaces repliés) appliqué **des deux côtés**, au stockage comme à la
  vérification, pour que "CONNERIE", "connerie" et "cônnerie" se rejoignent
- commandes mod `!gs banword`, `!gs unbanword`, `!gs banwords`
- `tests/moderation/bannedWordsService.test.ts` (SQLite réel, selon la règle du repo)

### Où le contrôle est placé, et pourquoi

Le filtre est **en amont de toute résolution payante** (SociaVault) et de la
synthèse TTS, donc un texte refusé ne consomme aucun crédit. Dans
`greenScreenCommand` il est aussi placé avant blacklist, permissions et
cooldown : le texte est refusé pour ce qu'il contient, indépendamment du reste.

Une entrée vide est refusée à l'ajout : stockée, elle ferait correspondre
n'importe quel texte.

### Vérification

360 tests verts, `tsc` propre, puis bout-en-bout contre un vrai serveur :
mod-only respecté, expression de plusieurs mots, refus d'un texte en majuscules,
retrait insensible à la casse, puis passage de nouveau.

Deux pièges rencontrés pendant cette vérification, à connaître pour la suite :

1. Un premier bout-en-bout avait conclu trop vite : le second envoi avait été
   arrêté par le **cooldown**, pas par le filtre, donc il ne prouvait rien. Il
   faut désactiver le cooldown du tenant semé, ou envoyer le texte interdit en
   premier.
2. Un cas accentué semblait passer le filtre. En instrumentant la route, le
   `caption` arrivait avec `U+FFFD` : c'est **curl dans ce terminal** qui abîmait
   l'octet UTF-8, pas le code. Envoyer l'accent en échappement JSON
   (`\u00ce`) donne un corps purement ASCII et lève le doute.

Au passage, la regex de `normaliseText` contenait les marques combinantes
**littérales** (invisibles dans un éditeur, et silencieusement cassables par un
ré-encodage) : elle est désormais écrite `[\u0300-\u036f]`.

### Session créée à la main pour tester `/api/simulate`

`getUserFromSession` passe par `ensureFreshAccessToken`, donc un utilisateur
semé avec un token expiré fait échouer la session (`unauthorized`) en tentant un
refresh Twitch. Pour un test local, semer `access_token` non vide et
`token_expires_at` dans le futur.

## Duo de personnages et liseré du décor (2026-10-14)

Deux retours de l'utilisateur sur la page viewers.

### Sonic et Tails s'éloignaient trop

Les deux traversées avaient des durées différentes (23s et 27s). C'était voulu
au départ — "que leur écart ne se répète pas" — mais deux durées premières entre
elles se déphasent indéfiniment : au bout d'un moment l'un est à 62vw quand
l'autre est à 0, et le duo se perd.

Correction : **même durée (25s), même point de départ, même point d'arrivée**.
C'est ce qui les garde ensemble. L'allure inégale vient uniquement des étapes
intermédiaires décalées, qui laissent l'écart s'ouvrir et se refermer.

Le réglage a été choisi en mesurant, pas à l'œil : un script simule
l'interpolation `ease-in-out` par segment comme le fait le navigateur et sort
l'écart sur tout le cycle. La variante retenue tient entre -4,3vw et +4,1vw, la
tête change de main (46% / 41% du cycle), et sur un écran de 1920px ils restent
entre 2px et 163px l'un de l'autre, donc sans jamais se croiser. La première
tentative descendait à -7,1vw, ce qui faisait passer Sonic devant Tails sur un
grand écran.

### Liseré violet autour du décor

Le crop d'origine avait gardé les séparateurs de la planche source, dans une
couleur (`rgb(186,65,70)`) absente de la liste de couleurs à retirer : un rang
en haut, et 2 colonnes à droite que le miroir avait repliées en une bande de 4
colonnes au milieu de la tuile. La répétition horizontale les faisait lire comme
des lignes verticales "sur les côtés".

Le comptage a montré que ces pixels vivaient **uniquement** là :
512 (rang 0) + 4x214 (colonnes 254-257) - 4 de recoupement = 1364, soit
exactement le total trouvé dans l'image. Retirer ce rang et ces 4 colonnes les
élimine donc tous, et comme les colonnes sont symétriques autour du centre la
tuile reste un miroir parfait.

Résultat vérifié sur le fichier produit : 0 pixel violet, 0 pixel brisant la
symétrie, et coût de la jointure de boucle à 0,0 contre 36,7 pour un voisinage
interne moyen. La tuile passe de 512x214 à 508x213 (manifeste mis à jour au même
zoom 3x, 1524x639) et le défilement, dérivé de `displayWidth`, a suivi tout seul.

### Côté tests

L'ancien test épinglait les valeurs de réglage (23s, 27s, 62vw, 55vw) et
affirmait `expect(23 % 27).not.toBe(0)` — une tautologie sur des littéraux, qui
ne testait rien du code et qui affirmait désormais l'inverse de l'intention.
Réécrit sur les invariants : durées égales, même départ et même arrivée, au
moins un pas en arrière de chaque côté, et écart maximal borné. Les deux
mutations (durées différentes, arrivée divergente) font bien échouer le test.

Rappel qui a coûté un faux échec : un script temporaire laissé à la racine sous
le nom `.test.js` est ramassé par vitest comme fichier de test.

## Sonic Mania et couche de parallaxe (2026-10-14)

### Sonic remplacé par le sprite de Sonic Mania

Le cycle de course vient de la ligne "Jog / Run / Dash" de la planche Mania,
cellules 12 à 19 : **8 images de 31x36**, affichées en 74x86 pour garder
exactement la hauteur que la page utilisait déjà, donc sans toucher à la mise
en page. À 32 fps le cycle dure 0,25s, soit le même rythme de jambes qu'avant
(4 images à 16 fps) : seule la finesse change.

Découpage fait en mesurant la planche, pas à l'œil : bandes de contenu par
ligne, puis cadres de cellule par colonne, et une **boîte englobante commune
aux 8 images** pour que la course garde son alignement au lieu que chaque image
soit centrée sur elle-même.

Deux pièges rencontrés :

1. La planche a **quatre** verts de fond (`0,240,0`, `0,138,0`, `0,170,0`,
   `0,111,0`). N'en retirer que deux laissait des barres vertes et faussait la
   boîte englobante, qui débordait sur la ligne voisine.
2. Il faut borner le balayage vertical à la ligne visée : les cadres de cellule
   des lignes voisines se touchent, et la détection remontait jusqu'à elles.

Vérifié avant intégration : les 8 images ont des comptes de pixels homogènes
(594 à 670), ce qui aurait révélé une image vide ou contaminée.

### Nouvelle couche `skyline` derrière les palmiers

Ajout d'un emplacement de sprite `skyline`, la plus lointaine : ciel, nuages,
montagnes et cascades, pris dans `Scene2-BG Outside 1.png` sur les lignes
y=0..147, en s'arrêtant là où commence la falaise pleine (qui aurait fait un
bloc sombre derrière les palmiers). L'image d'origine est prévue pour se
répéter : jointure horizontale à 22,0 contre 15,9 pour un voisinage interne
moyen, donc la boucle ne se voit pas.

**La parallaxe est calculée, pas écrite en dur.** `SKYLINE_SPEED_RATIO` dit
que la couche lointaine dérive à 45% de la vitesse des palmiers, et la durée
s'en déduit à partir des largeurs affichées. Redimensionner l'une ou l'autre
tuile ne fausse donc pas le rapport. Mesuré sur la page servie : 10,16 px/s
pour les palmiers contre 4,57 px/s pour le ciel.

Le haut de la couche s'efface par un `mask-image` en dégradé : sans lui, la
découpe du ciel tirerait une ligne nette en travers de la page, exactement le
défaut qu'on venait de corriger sur le `backdrop`.

### Tests

L'invariant testé est la parallaxe elle-même : **vitesse à l'écran** de la
couche lointaine inférieure à celle de la proche, et non une simple durée plus
longue sur une tuile plus large — les deux tuiles n'ont pas la même largeur,
donc comparer les durées ne voudrait rien dire. Vérifié par mutation : passer
le ratio à 1,6 fait bien échouer le test (16,25 px/s contre 10,16).

Testé aussi que la couche est peinte avant le `backdrop` et sous lui
(`z-index:-2` contre `-1`), et qu'elle reste opt-in comme les autres
emplacements.

## Les sprites corrigés n'arrivaient pas aux navigateurs (2026-10-14)

L'utilisateur voyait encore les bandes violettes du décor après le correctif et
le déploiement. L'image, elle, était bonne : un recensement de toutes ses
couleurs n'en donne que neuf, toutes de la palette Green Hill, et aucune
violette. Le défaut était ailleurs.

`GET /sprites/:file` répond avec `Cache-Control: public, max-age=86400`, sans
ETag ni revalidation, sous un nom de fichier qui ne change jamais. Un
navigateur qui tient déjà `backdrop.png` le garde donc jusqu'à 24 h, et aucune
correction d'image ne peut l'atteindre. C'est un défaut de conception introduit
en même temps que les sprites, pas un accident de ce correctif-là.

### Correctif

`loadSpriteSet` calcule une empreinte sha1 courte du contenu de chaque fichier
et la pose sur la définition du sprite ; `submitHtml` sert les URL en
`/sprites/<fichier>?v=<empreinte>`. Un fichier modifié devient donc une URL
différente, récupérée immédiatement, tandis que les fichiers inchangés gardent
le cache long. Un seul helper `spriteUrl` est utilisé par les quatre endroits
qui construisent une URL, pour qu'aucun emplacement ne puisse rester sur une
URL non versionnée.

Vérifié contre un vrai serveur : les cinq sprites portent une empreinte, la
route sert toujours le fichier malgré la chaîne de requête, et l'empreinte
annoncée dans la page correspond au sha1 du fichier sur disque.

### Leçon

Vérifier qu'un déploiement sert bien le nouvel octet ne suffit pas : encore
faut-il que le navigateur ait une raison de le demander. Les deux fois où j'ai
confirmé un déploiement par la taille du fichier servi, je mesurais le serveur,
pas ce que voyait l'utilisateur.

## Plus de repli sur l'embed TikTok (2026-10-15)

La bannière de cookies TikTok revenait sur le stream. Elle venait du repli
embed de `sociavaultResolve` : quand SociaVault ne rend aucun fichier lisible,
la fonction renvoyait `https://www.tiktok.com/embed/v2/<id>`, que l'overlay
affichait en iframe. Ce lecteur démarre muet et derrière la bannière, donc il
ne valait rien sur un stream — le commentaire du code l'admettait déjà.

### Ce qui change

`sociavaultResolve` renvoie désormais `null` dans ce cas. Les deux appelants
traitaient déjà le `null` correctement, donc le comportement devient :

- chat : "Impossible de résoudre cette URL TikTok."
- page viewers : `unsupported / tiktok_unresolved`

Supprimés avec lui : la branche iframe TikTok de l'overlay, le cas spécial
embed de `mediaPreview`, et le type `kind: "iframe"` devenu inatteignable —
ce dernier n'avait d'ailleurs aucune branche de rendu côté client, donc un
embed y était affiché comme un `<video>`, c'est-à-dire cassé.

### `sociavaultSearch` : corrigé, mais ce n'était pas la cause

La recherche par mots-clés renvoyait elle aussi systématiquement un embed. Elle
va maintenant chercher un vrai fichier : d'abord dans la charge utile de la
recherche, qui porte souvent déjà les adresses de lecture (**gratuit**), et
seulement sinon via `video-info` (1 crédit). Sans fichier, elle renvoie `null`.

À noter pour la suite : **cette fonction n'est pas câblée** dans l'app
(`tiktokSearch: undefined` dans `createTenantServices`, la recherche par mots
clés passe par YouTube). La correction est donc préventive, pas le remède au
symptôme signalé.

### Vérification

Bout-en-bout avec une clé API volontairement invalide, pour que la résolution
échoue pour de vrai comme chez l'utilisateur : le chat répond "Impossible de
résoudre cette URL TikTok.", la prévisualisation renvoie `tiktok_unresolved`,
et rien n'arrive dans l'historique. Aucune URL d'embed ne subsiste dans le code
(`grep` sur `tiktok.com/embed`).

Trois tests épinglaient l'ancien repli, c'est-à-dire exactement le défaut
signalé. Ils ont été réécrits sur le comportement voulu.

## Mini-éditeur avant envoi (2026-10-16)

La page viewers permet désormais de choisir un extrait (début/fin), la place
de la vidéo sur la source navigateur, et de voir le texte tel qu'il partira à
l'écran.

### La décision d'architecture

Les envois de la page viewers fabriquaient une chaîne `!gs <url> /N |texte`
et la passaient au routeur. Y ajouter un rectangle et deux timecodes aurait
donné une grammaire que personne ne peut taper ni lire.

Les réglages voyagent donc dans un champ structuré, `CommandContext.presentation`,
**à côté du message et non dedans**. L'envoi continue de passer par le même
routeur, donc blacklist, permissions, cooldown, approbation et validation
d'URL s'appliquent sans duplication — le principe du repo est préservé.

Le champ traverse ensuite `PlaybackItem` -> `PlaybackEvent` -> SSE -> overlay,
et **aussi la file d'approbation** : sans ça, un envoi approuvé aurait perdu
son montage en chemin.

### Règles de durée

Un extrait est la longueur la plus précise qui soit : il dit où le clip
commence et finit. Il l'emporte donc sur la durée du média et sur un `/N`
demandé en même temps, tout en restant borné par `max_video_duration_seconds`
du tenant. Le serveur en déduit `cutAfterSeconds`.

### Côté overlay

- Placement en **pourcentages** de la source, pour que le même envoi tombe au
  même endroit quelle que soit la résolution du Browser Source.
- Le placement est réappliqué à chaque envoi, **y compris à vide** : sans
  remise à zéro, un envoi cadré laisserait son cadre au suivant.
- Fichier vidéo : fragment `#t=<s>` pour démarrer sur l'extrait sans
  télécharger ce qui précède, repli sur `currentTime` si le serveur ignore les
  fragments, et fin pilotée par `timeupdate` — plus juste que le minuteur, qui
  compte depuis l'arrivée de l'évènement et non depuis le premier instant joué.
- YouTube : paramètres `start`/`end` du lecteur, en secondes entières.

### Côté page viewers

- Le texte est dessiné par-dessus la prévisualisation avec la police et le
  contour de l'overlay, dimensionné sur le cadre (`container-type:inline-size`)
  et non sur la fenêtre, sinon il paraîtrait énorme sur une prévisu étroite.
- La durée vient des métadonnées du fichier, ou du lecteur YouTube qui
  l'annonce par `postMessage` après la poignée de main `listening`. Le
  listener vérifie `ev.origin`. Sans réponse, les poignées restent cachées
  plutôt que d'afficher une échelle inventée.
- Glisser/redimensionner en `pointer events`, donc au doigt comme à la souris.
  Le cadre peut déborder, mais jamais au point de ne plus pouvoir être rattrapé.
- **Rien n'est envoyé tant que rien n'a été touché** : `collectPresentation()`
  renvoie `null`, et un envoi sans éditeur reste exactement ce qu'il était.

### Choix laissé à l'utilisateur

Le placement est **libre**, plein écran compris. La question lui a été posée
avec l'alternative bornée, en signalant qu'un viewer peut donc couvrir toute
la scène ou la facecam ; il a choisi le libre. Les garde-fous restent
`!gstop` et la file d'approbation.

### Vérification

388 tests, `tsc` propre, puis bout-en-bout contre un vrai serveur en écoutant
le flux SSE de l'overlay pendant l'envoi :

- avec réglages : `"En cours (8s)"` pour un extrait 12->20, et l'évènement
  `start` porte `cutAfterSeconds: 8` et la `presentation` intacte ;
- sans réglages : l'évènement ne porte ni `presentation` ni `cutAfterSeconds`,
  identique à avant la feature ;
- rognage incohérent (fin avant début) : 400, rien n'est routé.

Un faux routeur de test ne capturait que `rawMessage` et `user` : plus étroit
que le vrai contrat, il faisait passer l'assertion à côté du champ. Élargi.

## Le cadre ne tenait pas ce qu'il cadrait (2026-10-16)

Retour d'essai juste après la livraison du mini-éditeur. Deux défauts de ce
même lot, tous deux invisibles aux tests existants parce qu'ils portaient sur
des chaînes et non sur un rendu.

### 1. Les médias portrait ignoraient le cadre

`.yt-short-inner` et `.tk-short-inner` faisaient
`width:calc(100vh * 9 / 16)` : une mesure prise sur **la fenêtre**, pas sur le
conteneur. Un Short YouTube, un TikTok ou un reel gardaient donc leur taille
plein écran à l'intérieur d'un cadre réduit, et le placement choisi dans
l'éditeur n'avait aucun effet sur eux.

Remplacé par `height:100%` + `aspect-ratio:9/16`, qui se mesure sur le
conteneur. À pleine taille le résultat est identique à l'ancien calcul.

### 2. Le texte ne suivait pas le clip

La prévisualisation dessine le texte par-dessus le média ; l'overlay le posait
en bas de toute la source, hors de `#wrap`. Avec un clip cadré les deux se
contredisaient. Le `#caption` vit maintenant **dans** `#wrap`, dimensionné en
`cqw` sur le cadre.

Repli conservé : la déclaration `6vw` est gardée **avant** celle en `cqw`, pour
qu'un OBS dont le Chromium ignore les unités de conteneur rejette la seconde
et garde une taille lisible au lieu de retomber sur la valeur par défaut.

### Vérification par la mesure, pas par la chaîne

Les tests de cette zone comparent des chaînes, et c'est précisément ce qui a
laissé passer `100vh`. La vérification s'est donc faite en rendant **la vraie
feuille de style**, extraite de `getOverlayHtml()`, dans Chrome headless
(`--dump-dom`, géométrie écrite dans le DOM par un petit script) :

| | cadre 35%x30% | sans cadre |
|---|---|---|
| wrap | 666x296 | 1904x985 |
| colonne portrait | **166**x296 (9:16 du cadre) | 554x985 |
| taille du texte | 33,3px | 72px |

Avec le bug, la colonne aurait fait **554px** de large dans un cadre de 666px.
Et la colonne 554x985 du cas sans cadre est exactement ce que donnait l'ancien
`calc(100vh * 9/16)` : aucune régression.

Seul écart assumé : le texte remonte de 15px à pleine taille (4% au lieu de
24px fixes), le prix pour qu'il suive un cadre réduit.

### À retenir

Une règle CSS géométrique ne se teste pas en cherchant une sous-chaîne. Rendre
la vraie feuille de style dans un navigateur et lire les rectangles prend
quelques minutes et tranche pour de bon.

## OBS exécutait encore la page d'avant (2026-10-16)

L'utilisateur avait bien cadré un envoi YouTube et le cadrage n'a pas été pris
en compte. Le correctif précédent (unités de fenêtre) ne couvrait que le
portrait, donc il fallait savoir si son envoi était un Short ou un paysage.

### Ce que la mesure a dit

Les deux pistes évidentes ont été éliminées par la mesure, pas par la lecture :

- **CSS paysage** : rendu dans Chrome headless, `.yt-wrap` tombe exactement sur
  le cadre (666x296 à 60%/5%) et l'iframe le suit. Correct.
- **Trajet des données** : bout-en-bout avec une **URL YouTube** cette fois (le
  test précédent utilisait un `.mp4`), la `presentation` arrive intacte dans
  l'évènement SSE.

Donc ni le CSS ni le transport. Il restait une seule explication.

### La vraie cause

**Une source navigateur OBS garde la page qu'elle a chargée.** Un déploiement
ne la recharge pas : OBS continuait d'exécuter le script d'avant l'éditeur,
qui ignore `presentation` quel que soit le média. Même classe d'erreur que le
cache des sprites — vérifier le serveur ne dit rien de ce que le client exécute.

### Correctif permanent

La page porte une empreinte sha1 de sa propre source (`getOverlayVersion()`,
calculée une fois puis mémorisée), le serveur l'annonce dans l'évènement
`connected`, et une page qui se découvre périmée appelle `location.reload()` —
**une seule fois**, pour qu'un désaccord durable ne tourne pas en boucle.
L'`EventSource` se reconnectant tout seul, un déploiement suffit désormais à
rafraîchir l'overlay sans toucher à OBS.

### Le piège dans lequel je suis tombé en le corrigeant

J'avais ajouté la version dans `OverlayBroadcaster.connect()`, et le test
unitaire passait. Mais **OBS n'atteint pas ce chemin** : la route réelle est
`/overlay/:channel/events` dans `publicRoutes`, qui écrit son propre
`connected` via `streamSSE`. Sur le fil, l'évènement sortait toujours sans
version. Pris uniquement parce que j'ai relu le flux avec `curl` au lieu de
croire le test vert. Un test a été ajouté sur la route réellement utilisée.

### À retenir

Deux chemins écrivent un `connected`. Quand deux implémentations d'une même
chose coexistent, un test vert sur l'une ne dit rien de l'autre — il faut
vérifier celle que le client atteint vraiment.

## Le cadre ne peut plus déformer la vidéo (2026-10-16)

La poignée de redimensionnement changeait largeur et hauteur **indépendamment**
(`from.w + dx` d'un côté, `from.h + dy` de l'autre), donc on pouvait fabriquer
n'importe quelle forme. La vidéo ne s'étirait pas vraiment — `object-fit:contain`
la laissait intacte — mais elle se retrouvait entourée de bandes et plus petite
que le cadre annoncé : ce qu'on voyait dans la scène n'était pas ce qui sortait.

### Correctif

Le cadre prend la **forme du média** :

- initialisé au plus grand rectangle de cette forme qui tienne dans la source
  16:9 (`computeFit`) ;
- la poignée projette le geste sur la **diagonale** du cadre et multiplie les
  deux côtés par le même facteur :
  `scale = 1 + (dx*w + dy*h) / (w² + h²)`. Un geste purement horizontal ou
  purement vertical agrandit donc proportionnellement, et la déformation
  devient impossible par construction plutôt que par surveillance.

La forme vient du drapeau `portrait`, puis des pixels réels dès que
`videoWidth` / `naturalWidth` sont connus. `placeDirty` empêche une forme
arrivée sur le tard d'effacer un cadrage déjà posé à la main.

`placeTouched()` se compare désormais au cadre par défaut et non à "plein
écran" : pour un portrait, ce défaut est déjà une colonne, et c'est exactement
ce que l'overlay fait sans consigne. Rien n'est donc envoyé tant qu'on n'en a
pas bougé.

### Vérification

Encore une fois les tests de cette zone comparent des chaînes. La propriété
réelle a été vérifiée **en pilotant la vraie page** dans Chrome headless :
`pointerdown` / `pointermove` / `pointerup` sur la vraie poignée, puis lecture
du rectangle du cadre.

| | largeur x hauteur | rapport |
|---|---|---|
| glissement +220 / +8 px | 636 x 354 | **1,794** |
| glissement -10 / -120 px | 526 x 293 | **1,794** |

Deux gestes volontairement déséquilibrés, rapport identique : la forme tient.
Avec l'ancien code le premier aurait écrasé le cadre à plat.

Cohérence éditeur/overlay vérifiée séparément : le cadre par défaut d'un
portrait fait 31,64% de large, et la colonne 9:16 que l'overlay dessine seul
sur 1920x1080 fait 31,64%. La prévisualisation ne ment pas sur le rendu.

## Pincement et repère du streamer (2026-10-16)

Deux retours d'usage après la mise en ligne de l'éditeur.

### Pincer pour redimensionner

Le geste instinctif sur téléphone, et le multi-touch avait été négligé. Les
doigts sont suivis sur la **scène entière** (`pointerdown/move/up/cancel` sur
`#ed-stage`), et dès qu'il y en a deux le glissement en cours rend la main
(`if(pinch) return;` dans le handler de `beginDrag`), sinon les deux gestes se
disputeraient le cadre.

Le facteur est `distance / distanceInitiale`, appliqué aux deux côtés, et le
centre du cadre est conservé: le pincement ne peut donc pas plus déformer que
la poignée.

Vérifié en pilotant la vraie page dans Chrome headless avec deux `PointerEvent`
synthétiques: distance divisée par deux -> cadre à 50% exactement, rapport
inchangé (1,794 avant comme après), cadre recentré.

### Silhouette du streamer dans la scène

Pour que le viewer sache où ne pas poser la vidéo. Géométrie relevée sur une
capture de la scène de live, dans un repère 160x90 (la source 16:9):
tête `cx=92 cy=30 r=17`, buste de 44 à 140 en largeur. `pointer-events:none`,
sinon elle avalerait les gestes destinés au cadre.

**Codée en dur pour une seule scène**, dans la constante `STREAMER_SILHOUETTE`.
L'app étant multi-tenant, c'est une dette assumée et signalée: quatre nombres
en réglage de tenant suffiraient à la généraliser.

### Fausse piste notée pour mémoire

Une capture de la scène montrait ce qui ressemblait à une **seconde silhouette**
au-dessus du cadre. Diagnostic: `document.querySelectorAll('.stage-me').length`
vaut 1, et la scène est en `overflow:hidden`. C'étaient les **nuages
décoratifs** du fond de page (`radial-gradient` existants), visibles parce que
la sonde avait vidé le corps de page. Rien à corriger — mais compter les
éléments a coûté moins cher que de continuer à regarder l'image.

### Flux moniteur du streamer (`/overlay/:channel/monitor`)

Première brique d'un moniteur hors OBS (fenêtre transparente, sans ATH) qui
montre au streamer ce que fait GS Bot en direct. Le projecteur OBS a été écarté
(barre de fenêtre, pas de transparence), obs-websocket aussi (captures d'écran
interrogées en boucle, mot de passe à configurer).

Le flux réutilise le token overlay, relaie les évènements de lecture et ajoute
un évènement `queue` (lecture en cours, taille de file, approbations en
attente). Il ne crée ni ne retient le tenant, et a sa propre limite de 3
connexions. Piège rencontré en test: une coupure pendant une écriture déclenche
l'abort avant que la boucle ne dorme, d'où le test `stream.aborted` juste avant
l'attente — sans lui, la place restait prise une seconde de plus.

Reste à faire: la page en mode moniteur (son coupé, cadre 16:9, bandeau) et le
lanceur de fenêtre transparente.

### Page moniteur et fenêtre transparente (`monitor-app/`)

`?monitor=1` sur la page overlay: même rendu qu'OBS, mais vidéo, YouTube et TTS
coupés (le son repartirait sinon dans le micro), contour de la source, bandeau
d'état alimenté par l'évènement `queue`. Le flux moniteur annonce aussi
`overlayVersion`, pour que la fenêtre se recharge après un déploiement comme OBS.

`monitor-app/` est un petit Electron (JS sans build) : fenêtre sans bordure,
transparente, `alwaysOnTop` niveau `screen-saver`, clic droit pour la taille et
l'opacité, Ctrl+Maj+M pour laisser passer les clics. La fenêtre n'est pas
redimensionnable à la souris: une fenêtre transparente redimensionnable se
comporte mal sous Windows, donc la taille passe par le menu, qui garde le 16:9.
Vérifié sur Windows 11 contre un flux scripté. Pas encore d'exécutable empaqueté.

**Fond noir pendant les vidéos** : avec l'accélération matérielle, Windows peint
toute la fenêtre transparente en noir dès qu'une vidéo joue (bandes autour d'une
vidéo verticale ou 4:3). Couper les surcouches DirectComposition n'y change rien;
`app.disableHardwareAcceleration()` règle le problème, vérifié par captures. Le
fond flou des Shorts est masqué en mode moniteur.

### File d'attente qui paraît bloquée

Symptôme remonté: une fois la file pleine, plus rien ne s'affiche et il faut la
vider à la main. Cause: le serveur passait au suivant uniquement à la fin de
`durationSeconds`, une estimation, alors qu'un lien mort, une vidéo YouTube non
intégrable ou une vidéo plus courte laissent l'écran vide bien avant. Chaque
lecture porte maintenant un `playbackId`, l'overlay le renvoie sur
`POST /overlay/:channel/ended` quand le média quitte l'écran, et
`PlaybackQueue.finishCurrent()` enchaîne. Vérifié dans un navigateur contre un
flux scripté: un clip de 3 s annoncé à 600 s est signalé à 3,7 s, un lien 404
aussitôt, un arrêt décidé par le serveur ne renvoie rien. Les logs de prod
n'étaient pas accessibles: la cause est déduite du code, pas observée en prod.

### Bouton Stream Deck d'arrêt

`GET|POST /overlay/:channel/stop?token=<overlay_token>` fait la même chose que
`!gstop`. GET est accepté exprès : l'action « Site web » du Stream Deck, cochée
« Accès en arrière-plan », envoie un GET sans plugin à installer. Le lien est
affiché et copiable dans le dashboard, sous l'URL OBS (même token, il suit une
régénération). `PlaybackQueue.stop()` émet désormais toujours
`{ type: "stop", emergency: true }`, même à vide, et l'overlay coupe alors aussi
le TTS, qui pouvait survivre à son clip. Vérifié dans un navigateur : une
légende TTS de 60 s disparaît à l'arrêt. L'ancien `streamdeck-plugin/` vise une
API de contrôle supprimée et n'a pas été touché.

### Cooldown par viewer

Les colonnes `cooldown_per_user` / `cooldown_per_user_seconds` existaient déjà
sans être exposées, et le cooldown par viewer ne jouait que si le cooldown
global était actif. Il est maintenant indépendant : un viewer ne peut envoyer
qu'une vidéo toutes les N s, les autres restent libres. Mods et streamer en sont
exemptés (pas du global). Les noms sont comparés sans la casse, les invités de
la page viewers partagent le pseudo `invite` donc un seul cooldown. Réglable
dans le dashboard et par `!gs usercooldown on|off|<n>`. Le refus dit au viewer
quand il pourra renvoyer (`scope: "user"` dans la décision).
